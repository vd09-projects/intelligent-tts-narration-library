# scripts/gso-requirements.txt — GPT-SoVITS (GSO) torch inference worker (issue #161)

# The pinned dependency set for scripts/gptsovits_worker.py. Installed into a
# DEDICATED venv (.venv-gso) by `make gso-worker-venv` — NOT the shared .venv (kokoro-
# onnx) and NOT .venv-rvc (which is torch-FREE). This worker is the INVERSE of the RVC
# worker: it REQUIRES torch and asserts torch PRESENT at startup (torch is the engine
# here). Torch stays isolated to this subprocess venv and is NEVER linked into any Go
# binary — the subprocess boundary is what keeps it (and the mixed-license transitive
# GPT-SoVITS stack) out of the library. Python 3.10–3.12 ONLY (funasr/pyopenjtalk/
# jieba_fast target 3.10–3.12) — NEVER system 3.14.
#
# HARD RULE: every line is an exact `==` pin. Never a `>=`, never a bare name.

# ── Provenance — RE-DERIVED 2026-07-27 (issue #165 machine-run acceptance) ─────
# This is the FULL transitive closure captured from the on-machine PROVEN venv
# `pip freeze` (the ~/repos/GPT-SoVITS-local/.venv that produced working v2Pro
# inference in docs/gpt-sovits-inference-runbook.md), on Apple M1 Pro / Python 3.11.13.
# It supersedes the earlier PENDING pins.
#
# AC3 conflict resolution (the flagged numpy 2.1.3 / numba 0.60.0 conflict): numba
# 0.60.0 caps numpy < 2.1 and the funasr/librosa/GPT-SoVITS stack is numpy<2 anyway,
# so the earlier numpy 2.1.3 pin was unsatisfiable. RESOLVED to the proven pair:
#     numpy==1.26.4  +  numba==0.66.0  (llvmlite==0.48.0)
# Torch-trio alignment held at the runbook versions (all mutually consistent here):
#     torch==2.13.0 · torchaudio==2.11.0 · torchcodec==0.15.0
#
# ── The gotchas that touch this file / the venv build ───────────────────────
#   1 (install order): `make gso-worker-venv` installs torch+torchaudio FIRST, then
#     torchcodec, before this file's remainder resolves. (Listed here too; already-
#     satisfied when the -r step runs.)
#   2 (opencc build fails on arm64): a BARE `opencc` is DELIBERATELY ABSENT. Only the
#     drop-in `opencc-python-reimplemented` (same `opencc` import name) appears below.
#     The venv target's `^opencc` filter is a harmless no-op against the reimpl line.

#   4 (NLTK data): downloaded at venv BUILD time by the target, not a pip dep here.
#   5/6/7 are runtime request-validation gotchas in the worker, not deps.
