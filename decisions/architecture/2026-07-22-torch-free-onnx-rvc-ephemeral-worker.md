## Context

We have two trained RVC voices (Applio-flavored: RVC v2 / 40kHz / f0 / vocoder=HiFi-GAN / contentvec — `cool-jahns`, `confident-neal`; `.pth` + faiss `.index`). We want them as an efficient, tech-stack-consistent voice-repaint step inside the Go narration pipeline (Kokoro writes the words → RVC repaints the timbre). Today inference shells out to an external Applio clone via `core.py infer` **per clip**, paying a full torch+faiss cold start every call and hitting a faiss+torch OpenMP segfault (worked around with `KMP_DUPLICATE_LIB_OK` / `OMP_NUM_THREADS`).

Hard constraints: M1 Pro / 16GB / CPU-only (MPS segfaults) / local + free; **reuse the two trained voices** (no retrain); keep the faiss index usable (index_rate 0.5–0.75 = quality); **quality parity judged by ear**. Soft leans (explicitly not fixed): Go, ONNX, torch-free. Researched via huginn (DEEP): 50 candidates discovered, then the finalist path was piloted end-to-end on this machine.

## Options considered

### Option A: keep shelling Applio `core.py` per clip (status quo)
- **Pros**: works today; exact quality.
- **Cons**: full torch+faiss cold start every block; faiss/torch OpenMP segfault; hardcoded external Applio dependency. Rejected.

### Option B: warm / long-lived RVC daemon
- **Pros**: amortizes load fully; per-clip warm ~7s.
- **Cons**: holds ~3GB **idle** between jobs — user explicitly wants RAM free for other heavy tasks. Keep-alive only saves ~2s/clip over cold. Rejected.

### Option C: torch-free ONNX (onnxruntime + numpy + faiss) in an ephemeral per-job worker — **CHOSEN**
- **Pros**: torch-free at inference (kills the segfault at its root — no torch co-loaded); **faster than torch** (cold and warm); ONNX matches the repo's existing kokoro-onnx stack; per-job worker = load once per document, warm across blocks, exit → **0 idle RAM**; keeps the exact faiss index; parity confirmed by ear.
- **Cons**: a Python process stays in the stack; DSP front-end + export are bespoke (but proven in the pilot).

### Option D: fully in-process Go (onnxruntime-go + go-faiss / Go kNN)
- **Pros**: pure Go, no Python; maximal tech-consistency.
- **Cons**: runs the **same onnxruntime native lib** as C → **no speed gain over a warm C worker** (pilot-confirmed reasoning); costs un-deferring CGo (a standing repo decision) + reimplementing the RVC DSP front-end (STFT/htk-mel/Butterworth/resample) + kNN in Go. Deferred as the endgame, to ride the future `sherpa-onnx-go` CGo migration where Kokoro+RVC share one in-process ONNX runtime.

### Option E: rvc-python / MLX-native RVC / CoreML worker
- **Pros**: turnkey-ish; MLX reportedly faster on Apple GPU.
- **Cons**: still Python; reimplementation-parity risk; none beat C's proven parity+speed for our specific models. Not chosen (C dominates on evidence).

### Option F: swap the voice-conversion family (knn-vc / seed-vc / FreeVC / so-vits-svc) or bake timbre into a fine-tuned TTS
- **Cons**: all discard the trained `.pth`+`.index` (hard-constraint violation); seed-vc is GPL (repo is GPL-averse); fine-tuned-TTS was already tried and rejected (runbook §0). Rejected.

## Decision

**Torch-free ONNX (Option C), driven by an ephemeral per-job Python worker, wrapped as a Go `render.Renderer` decorator over the sherpa (Kokoro) renderer.** The worker loads the ONNX models + faiss index once per `Render` call, converts every block warm, then **exits** — zero idle RAM. Output is 40kHz end-to-end when RVC is on. A shared `buildRenderer(voice)` helper is the common code both CLI (`--voice`) and MCP (`voice` arg) call. Worker-unavailable → hard error (honesty rule), never silent substitution. **D (in-process Go) is the deferred endgame**, folded into the eventual `sherpa-onnx-go` CGo migration because it shares the same onnxruntime native library and buys no additional speed today.

## Consequences

- A lean torch-free venv (onnxruntime + numpy + faiss + scipy + librosa) is added for the worker; torch is used only at export time (offline).
- Big artifacts: `net_g.onnx` (~105MB/voice) + shared `contentvec.onnx` (360MB) + `rmvpe.onnx` (345MB) + index vectors (557MB) — gitignored, HF-backed, generated by `make rvc-export`.
- 40kHz-when-RVC means the persistent sink must read `Format.SampleRate` (not assume 24000) — a build-time verification item.
- Per-clip convert is ~7s (RTF ~0.45) on CPU — inherent to RVC; a full document's RVC time is minutes. Unchanged by C-vs-D.
- `mmap` demoted to an optional tuning flag: its RSS win (2.75 vs 3.70GB) is a single-convert measurement that evaporates across a multi-block job (pages fault in → ~3.9GB). Full-load is the default.

## Experiments

Piloted on M1 Pro (10 cores, 16GB, CPU) with the `cool-jahns` voice, fixed 15.5s clip. Artifacts + scripts in scratchpad `pilot-d/` (`PILOT_REPORT.md`, `BENCH_REPORT.md`).

**Parity (torch-free ONNX vs Applio torch):** per-stage corr ≥0.9999 (contentvec/rmvpe/net_g), DSP-glue corr 1.0, 100% exact pitch buckets, full-pipeline log-mel corr 0.982, matched peak/RMS, no artifacts. Raw-sample gap (corr 0.905) is only the RNG the torch reference itself re-randomizes. **User confirmed parity by ear.**

**Cold/warm/RAM benchmark (15.5s clip):**

| path | cold (load+1 convert) | imports | warm/clip | peak RSS |
|---|---|---|---|---|
| ONNX full-load | 9.55s | 0.81s | 6.93s | 3.70GB |
| ONNX mmap | 8.90s | 0.70s | 6.91s | 2.75GB |
| Torch (Applio) | 15.36s | ~5.5s | 8.35s | 4.48→5.89GB |

ONNX cold beats torch cold by ~6s (the torch import tax); ONNX convert is also faster (multithreaded ORT vs torch pinned single-thread by the faiss/libomp clash). Keep-alive saves only ~2s/clip for ONNX → ephemeral exit-after-job chosen. Bonus finding: Applio's `pipeline()` re-reads the 573MB index + re-instantiates RMVPE on every call; the ONNX path (sessions as globals) has no such wart.

## Revisit trigger

Reconsider **D (in-process Go)** when the `sherpa-onnx-go` CGo migration lands (CLAUDE.md's deferred in-process upgrade path) — at that point Kokoro + RVC can unify on one in-process onnxruntime C lib, making D nearly free. Also reconsider if a mature pure-Go or purego ONNX runtime covers the graph (GRU/attention/RandomNormalLike) without CGo, or if the per-clip CPU latency (~7s) becomes a UX blocker.
